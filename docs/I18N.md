# ISO Smart MedSupplier I18N

## Idiomas soportados

- `es-LATAM`: idioma nativo, default y fallback principal.
- `en`: inglés.
- `pt`: portugués.

La preferencia se guarda en `localStorage` con la clave `isosmart_language`. Si el valor guardado no está soportado, el frontend vuelve a `es-LATAM`.

## Arquitectura

El frontend usa un provider propio en `frontend/src/context/I18nContext.jsx`. No usa `i18next`.

APIs disponibles:

- `useI18n()`
- `t(key, fallback?)`
- `t(key, values)`
- `t(key, fallback, values)`
- `translateBackendString(value)`

Los diccionarios viven en `frontend/src/i18n/messages.js`.

## Convención de claves

Usar claves semánticas, no nombres genéricos:

- `common.*`
- `header.*`
- `navigation.*`
- `medsupplier.dashboard.*`
- `medsupplier.workspace.*`
- `medsupplier.sections.<sectionKey>.*`
- `medsupplier.fields.<fieldName>`
- `medsupplier.columns.<fieldName>`
- `medsupplier.values.<backendValue>`
- `medsupplier.workflow.*`

Ejemplos:

```jsx
const { t } = useI18n();

<button>{t('medsupplier.workspace.refresh')}</button>
<p>{t('medsupplier.workspace.recordsInScope', { count })}</p>
```

## Estados backend

No mostrar valores backend crudos como `active`, `on_hold`, `under_review`, `supplier_private` o `accepted_with_deviation`.

En MedSupplier se mapean con:

```jsx
t(`medsupplier.values.${normalizeValueKey(value)}`, value)
```

El valor enviado o recibido por API no se modifica; solo se traduce la representación visible.

## Formularios y tablas

Los formularios dinámicos de `medsupplierSections.js` mantienen sus nombres técnicos, recursos y contratos. La UI traduce:

- labels de campos con `medsupplier.fields.*`
- columnas con `medsupplier.columns.*`
- opciones select con `medsupplier.values.*`
- workflow actions con `medsupplier.workflow.*`

No agregar labels visibles nuevos sin claves en `es-LATAM`, `en` y `pt`.

## Fechas y números

Usar el idioma activo para formato visual:

- `es-LATAM` -> `es-ES`
- `en` -> `en-US`
- `pt` -> `pt-BR`

No convertir moneda ni cambiar moneda de negocio sin una regla explícita.

## QA i18n

Desde `frontend/`:

```bash
npm run i18n:check
npm run lint
npm run build
```

`npm run i18n:check`:

- compara claves entre `es-LATAM`, `en` y `pt`
- falla si hay claves faltantes críticas
- reporta claves usadas pero no definidas
- lista posibles hardcodes visibles para revisión manual

## Validación manual recomendada

1. Entrar al sistema.
2. Cambiar a inglés desde el header.
3. Recorrer dashboard, sidebar, workspace, tablas, formularios, modales y acciones.
4. Confirmar que estados backend visibles aparecen traducidos.
5. Cambiar a portugués y repetir.
6. Cambiar a español y confirmar fallback.
7. Recargar navegador y confirmar persistencia.
8. Probar desktop, tablet y mobile, especialmente textos largos en tablas y botones.

## Restricciones conocidas

- El script `i18n:check` reporta posibles hardcodes en módulos heredados no enlazados en las rutas principales de MedSupplier; revisar antes de volverlos rutas visibles.
- `frontend/src/i18n/messages.js` es grande y Babel muestra una nota de deoptimización al lint/build. No es error, pero conviene dividir diccionarios por dominio en una iteración posterior.
